# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The intro/landing site for Slang, a customer communication platform. A short single-page site (Nav → Hero → "What Slang is" → Product Tour → Connect → Footer), not a full marketing site. It was copied clean out of a Lovable-generated repo (`slang-conversations-connected`) with the Lovable history/metadata stripped; this repo's own git history starts fresh.

## Commands

```bash
npm install
npm run dev          # dev server (Vite)
npm run build        # production build
npm run build:dev    # build in development mode
npx tsc --noEmit      # type-check only, no build
npm run lint          # eslint .
npm run format         # prettier --write .
```

No test suite/framework is configured in this repo.

### Local SSR preview

`npm run preview` / `vite preview` does **not** work out of the box here: the default Nitro preset (`cloudflare-module`, see Deploy below) can't run locally that way. To actually run the built server locally:

```bash
NITRO_PRESET=node-server npm run build
NITRO_PORT=4321 node .output/server/index.mjs
```

Clean `dist .netlify .output .vercel .wrangler node_modules/.nitro` between builds with different presets: leftover manifests from a prior preset/build can cause the server to serve stale asset hashes (404s/500s) or a previous session's stale process can still be bound to the port. Check `netstat`/kill anything already listening before starting a fresh one.

## Architecture

### Routing (TanStack Start, file-based)

`src/routes/`: every `.tsx` file is a route (see `src/routes/README.md` for the full convention table: `index.tsx` → `/`, `users/$id.tsx` → `/users/:id`, `_layout.tsx` for layout routes). `src/routes/__root.tsx` is the only root layout (renders `<html>/<body>`, mounts `<ParticleField />` and `<ThemeToggle />` globally, holds the pre-hydration no-flash theme script). `src/routeTree.gen.ts` is auto-generated by `@tanstack/router-plugin`; never edit it by hand. `src/router.tsx` creates the router instance (React Query context, scroll restoration).

### SSR error handling

A deliberate three-part pipeline exists because h3 (Nitro's request handler) swallows in-handler throws into a generic `{"status":500,"unhandled":true,"message":"HTTPError"}` response with no stack trace:
- `src/lib/error-capture.ts`, wraps `console.error` and window error listeners to capture the *original* error out-of-band before h3 discards it.
- `src/server.ts`, the SSR entry point (`vite.config.ts` points `tanstackStart.server.entry` here instead of the framework default); inspects responses for the swallowed-error shape and re-renders a proper error page using the recovered error.
- `src/lib/error-page.ts`, renders that fallback HTML.
- `src/start.ts`, server-side request middleware (catches thrown errors before they reach h3) plus the CSRF middleware for server functions; defining this file opts out of Start's automatic CSRF middleware, so it's re-added explicitly here.

`src/lib/lovable-error-reporting.ts` (wired into `__root.tsx`'s error boundary) is a no-op outside the Lovable editor preview: a harmless leftover, not something to hook up to a real error service.

### Theming, everything is CSS variables

`src/styles.css` (Tailwind v4, CSS-first config: `@theme inline`, `@utility`, no `tailwind.config.ts`) defines every color as an OKLCH custom property in `:root` (dark, default) and again in `[data-theme="light"]` (a full light theme: background/foreground/surfaces/borders/shadow, not just accent hue). `ThemeToggle.tsx` toggles `document.documentElement.dataset.theme` between unset and `"light"`, persists to `localStorage` (`slang-theme`), and `__root.tsx` has an inline pre-hydration script to avoid a flash of the wrong theme. Because every component reads color exclusively through these variables (`--violet`, `--blue`, `--primary`, `--surface`, `--hairline`, etc., bridged to Tailwind utilities via `@theme inline`), adding or adjusting a theme is a CSS-only change; no component should ever hardcode a raw color (grep for `bg-white`/`text-black`/literal `oklch(...)` in components before adding one; past instances of this had to be fixed when the light theme was added).

### Motion system

Everything here is hand-built (no Framer Motion/GSAP) and centered on one hook:
- `src/hooks/use-reveal.ts` + `src/components/site/Reveal.tsx`, one-shot `IntersectionObserver` scroll reveal, CSS-class-driven (`.reveal`/`.reveal-in` and direction variants in `styles.css`). Reused everywhere a scroll-trigger is needed rather than adding a second system.
- `src/components/site/RevealText.tsx`, word-by-word reveal built **on top of** the same `useReveal` hook (one observer per block, words staggered via CSS `transition-delay`), not a separate mechanism.
- `src/hooks/use-tilt.ts`, `src/hooks/use-magnetic.ts`, small cursor-reactive hooks (product-frame tilt, CTA magnetic pull), element-scoped listeners only (no global mousemove cost when not hovered), no-op under `prefers-reduced-motion` or on coarse/touch pointers.
- `src/components/site/ParticleField.tsx`: the ambient background particle field, `react-three-fiber`/`three.js` instanced capsule meshes (two color layers reading `--violet`/`--blue` so it re-themes for free). Mounted once in `__root.tsx`. Skipped entirely (no canvas mounted at all) under `prefers-reduced-motion`. Note: resolving a CSS color to something `THREE.Color` can parse needs a canvas pixel-readback (`toRgbString` in this file); `getComputedStyle(...).color` is not reliable for `oklch()` values in this stack, since it can echo the raw string back unconverted.
- The `Reveal`/`RevealText` polymorphic `as` prop is typed as a narrow literal union (`"div" | "li" | "h1" | ...`), not `React.ElementType`, `@react-three/fiber` globally extends `JSX.IntrinsicElements` with hundreds of three.js element types, which breaks generic `ElementType`-based JSX typing (collapses common props to `never`). Keep this narrow if extending these components.

### Product visuals are hand-built, not screenshots

`ProductFrame.tsx` (browser-chrome wrapper) plus `DashboardMock.tsx` and `ProductMocks.tsx` (`InboxMock`, `CustomersMock`, `TeamMock`) render fake product UI entirely in CSS/JSX. This is deliberate, not a placeholder: the original Lovable-era assets were wired through `src/assets/*.png.asset.json` pointer files whose URL (`/__l5e/assets-v1/...`) only resolves inside Lovable's own dev server, broken on any real deploy. Those `.asset.json` files are still in `src/assets/` but unused; don't wire new `<img>` tags to them.

### UI primitives vs. site components

`src/components/ui/` is generic shadcn/ui (`components.json`: style `new-york`, aliases `@/components`, `@/lib`, `@/hooks`, `@/components/ui`); treat as a library, extend via the shadcn CLI/pattern rather than hand-editing broadly. `src/components/site/` is this project's actual page content/composition.

### Deploy target auto-detection

`vite.config.ts` sets `nitro: true` (not a hard-pinned preset) so platform auto-detection (`std-env` reading `VERCEL`/`NETLIFY` env vars, which each platform's build system sets automatically) picks the right Nitro output for whichever platform runs the build. `vercel.json` and `netlify.toml` each just set the build command so both platforms deploy from this one repo with no manual dashboard config. Don't hard-pin a preset back in `vite.config.ts` without a reason: that's what breaks the dual-deploy setup.

### ESLint note specific to this stack

`no-restricted-imports` blocks the `server-only` package: this is a Next.js convention that doesn't apply to TanStack Start; use a `*.server.ts` filename or `@tanstack/react-start/server-only` instead.
